# Polterware Agent Instructions

## Communication and editing

- Speak to Erick in Brazilian Portuguese.
- Write code, UI strings, technical documentation, commits, logs, and identifiers in English.
- Preserve unrelated work and make the smallest safe change.
- Do not create branches or commits unless explicitly requested.
- Do not run browsers, previews, distributions, or development servers unless explicitly requested in the current task. Automated tests and builds may run by default.

## Work cards

- Codex and other agents: run `polterware format` once for the Polter core (Work cards; `polterware format structure|decisions|facts|feature` for the rest), read with `polterware query cards`, and write Work cards with `polterware apply <file|->` (frontmatter `summary` and `rationale`). Claude Code gets the same through the `plugins/polterware` plugin (a symlink to `backend/providers/agentsetup/plugin`, which the binary embeds); `polterware setup claude|codex` installs it, and `polterware hooks enable|disable <name>` switches its hooks. The `context` hook (PostToolUse on `Read|Edit|Write|MultiEdit`) adds the brief of the Structure node a file belongs to once per session, again when that brief changes (`hook_context_seen`, because the core exits when idle); `polterware status` and its SessionStart hook add a line when the installed plugin or skill is older than the binary.
- Codex and other agents: start a session with `polterware status` and end it with `polterware handoff`.

## Product positioning

Polterware's category is **Project Context & Change Intelligence for AI Coding**: every agent and person reads the same project state, the Rules are the law agents read before they change anything, and each card shows the commits that did its work. The shipped wedge is Rules, Canon facts, the agent brief and search, Context Compiler, stable MCP reads, card Commits, AgentRun, audited MCP writes, CLI, Unified Change History, the Polter format with Work cards, Structure, Canvas, the Inbox, and the decision lifecycle. Integrations remain as a Connect UI only.

[`docs/future.md`](docs/future.md) is the only planning document and lists what is **not** implemented (Cloud, Jev, enrichment backlog, research). It is direction, not shipped behavior; never present its items as shipped. The code, this file, `polterware --help`, and `polterware format` describe what exists.

## Current product boundary

Polterware is both the umbrella and the main local-first app (`apps/polterware-desktop`), alongside Polterware Notes and Polterware Vitals. Polterware's first version is a local SQLite-backed Desktop with project surfaces Inbox, Milestones, Structure, Canvas, Knowledge, Agents, and Activity. Project switching happens on the Projects screen, reached through the Home button in the title bar, before entering a project. Project settings is fixed in the sidebar footer; App settings is the gear next to Commander in the title bar. Inbox is the default route.

The umbrella is an ecosystem, not a list: apps and tools live under Polterware only when they can integrate with the others. See [`docs/ecosystem.md`](docs/ecosystem.md) for the admission criteria and the current roster.

The Desktop supports multiple local projects and environments. It has no hosted or shared workspace model. One local core process (`polterware serve`) per database is the only process that opens SQLite (it is a detached daemon guarded by a lock, with a build handshake); Electron Main, the CLI, the TUI, and the MCP bridge attach to it or start it. The renderer reads and writes through `window.polterware` only.

A project is a name and its environments, with no folder: Create project asks only those. Repositories belong to components, optionally (the `repositories` table: name, GitHub identity `github.com/owner/repo` from the clone's remote, and this machine's clone as `local_path`). A node's Checkout picks one or chooses a folder (Polter `dir: <clone>`, which creates or reuses the repository), several components may share one, and the last component to unlink a repository removes it; with exactly one repository a node with no `repo` uses it. `polterware init` links the folder it runs in as the first component (`--no-dir` starts empty), `polterware repo list` reads them, and the CLI finds the project of the current directory by its repository clones.

- Integrations: detect CLI binaries, start provider authentication commands in a core-owned PTY, optionally open provider documentation through Main `openExternal`, and probe connection status. Credentials stay in the OS/CLI credential store. **KEEP** as the Connect path (not a provider console).

Platform CLIs live in Project settings (Platforms: Connected and Catalog), because connections belong to a project and its environments. The coding agent tooling (MCP, setup, hooks, the skill, the CLI reference) and the local core live in App settings. Never persist provider credentials in SQLite or add app-owned provider-token fields. Raw PTY output is not guaranteed to be sanitized; do not describe it as redacted.

## Polterware Notes (second app)

The monorepo also hosts Polterware Notes, a separate local-first app with its own core (`notes/backend`), contracts (`notes/schemas`), desktop (`apps/notes-desktop`) and feature packages (`packages/features/notes-*`). Polterware Notes shares `packages/frontend` and the UI law above but not Polterware's product surfaces, store or core: do not mix their data models, and keep the Polterware product boundary above unchanged. Polterware Notes checks run through `bash tooling/verify-notes.sh`; its renderer talks only through `window.pwnotes`.

## Architecture boundaries

- Go local authority: the single `polterware` binary (`backend/runtimes/cli`: TUI, commands, `serve`, `mcp`) and retained domains only.
- Desktop: Polterware, `apps/polterware-desktop`, with thin Electron Main, typed preload bridge, and Solid renderer.
- Features: `packages/features/<feature>`.
- Shared frontend: `packages/frontend`.
- Contracts: `schemas` to generated Go code in `backend/platform/gen` and TypeScript in `packages/contracts`.
- Renderer access: `window.polterware` only; no raw Electron or Node.js.
- The core uses a technical bearer session token without an account directory.
- There is one clean SQLite baseline and no compatibility requirement for earlier databases.

## Product navigation

- Agent reads: `polterware brief <card slug|Structure path|file>` (`polter.query "brief …"` over MCP) is the one read before work: the target with kind and technology, then its Rules (the node's own, its ancestors' marked `(from <path>)`, and the whole project's, never cut by the budget and binding on agents), open tasks and questions, the last handoff, the card's invariants, governing decisions with their statement, facts scoped to the target's path, the milestone goal, canvas links, and doc titles, in that order, deterministic and cut from the end to a token budget. A file resolves to the node with the longest `repo` + `path:` prefix. `polterware search <terms>` (`context` is an alias) lists matching nodes, cards, Rules, decisions, docs, and facts one line each. The format is layered the same way: `polter.SpecCore` (about 360 tokens, declared in `SpecCoreTokens` and checked to 10%) is what `polterware format`, `polter.format`, and the plugin skill carry; Structure, Rules, Decisions, Facts, and the feature flow are topics read on demand. `backend/tests/integration/token_budget_test.go` ratchets what agents read.
- Checkout projections: `polterware export` writes Decision files under `docs/decision/` and the generated block of each checkout's AGENTS.md (the Rules first, the project's and each applicable node's with `(from <path>)`, then principles, the checkout's Structure nodes with kind and technology, governing decisions, and the `brief` line); it never reads them back. AGENTS.md sync is opt-in per project (`project_settings.agents_sync`, `polterware export --sync on|off`, `WorkService.SetAgentsSync`, or the switch in Project settings › General): the core rewrites only the block, only when it changed, a moment after a write that can affect it; Decision files stay on the explicit export.
- MCP: four tools. `polter.query` takes every `polterware query` read, including `show <id>` (one card, Rule, Decision, fact, doc, entity, or run), `commits <slug>`, and `conflicts` / `conflict <slug>`; `polter.apply` writes Polter text; `polter.format` returns the core or a topic; `doc.upsert` writes a doc with a Markdown body. Writes join the session's AgentRun without a start or complete call, and a retired tool name returns an error naming its replacement. A Rule is a `#### rule <slug>: Statement` block with `scope:` (Structure paths; none is the whole project) and `status: removed`, written with a reason; a node's `! text` line is a Rule scoped to that node. A Fact is a statement with its scope; evidence is retired, and `evidence:` is refused. A Conflict is a `#### conflict <slug>: <the request>` block with `rule:` or `decision:` (the law it goes against), optional `card:` and `options: a | b`; an agent raises one instead of acting against a Rule or Decision and goes on with work it does not block, `answer:` decides it and `status: withdrawn` drops it (`polterware conflict raise|decide|wait|withdraw|list`; `wait` blocks until a person answers, and `polterware status` lists the answers of the last day).
- Inbox: master/detail page of derived items, grouped by kind — Conflicts (a request an agent raised against a Rule or Decision; the detail shows the request and what it goes against, and Decide picks an option or takes another answer; `inbox.KindConflict`), Questions (open card questions), Setup (a deploy whose provider CLI is not connected; `inbox.KindSetup`) — with the active item's detail on the right, closed until a row opens it and closable, like Activity's (the first item starts active; J/K or a row opens it again, and a resolved item hands over to the next). H moves the active item or the selection to Later (`defer`) and D dismisses it (`ignore`); count in the sidebar, also in `polterware status` and `polterware inbox`. Selected items take an action they all offer (Later, Dismiss) at once. The UI uses plain words throughout: stage ids `shape|plan|build|verify|delivered` read Idea, Planned, In progress, In review, Done; Decision states `challenged|superseded` read Under review and Replaced; the section names are Knowledge (route `truth`) and Agents (routes `dispatch*`, with Runs, Models, and Usage); ids, Polter keys, and the CLI keep their names.
- Milestones (the `milestones` route, formerly Work; `work` redirects): each milestone is a board of Work cards, with Board and Specs as its layouts
  - The section opens on the Roadmap, a table of the boards with no tabs: All cards (every card of every board) first, then the milestones in order with state, delivered/total progress, and target date. A row opens that board, a route of its own (`ClientRoute.milestone`, remembered per section): its toolbar has Back and the Board and List tabs at the start and the actions at the end. Cards with no milestone are in All cards (grouped by milestone, the List shows them under Backlog). A compact branch tree on a card on the left, hidden and shown from the toolbar's sidebar button, with its own search and filter (level and component kind; F) at its top that keep the ancestors of each match, the active filters showing under the toolbar, (texture +/- keys with curved guides) whose rows are one line: a tile with the level's glyph, the title, and on hover, Add domain on the project and Add component on a domain. The toolbar holds the tree toggle at the start and Draw as canvas at the end, with no band or fade: the document scrolls up under it; the toolbar has no search, filter, or add button; Draw as canvas (`drawStructure` in `packages/features/canvas`) draws the tree the same way every time on the agent-visible Structure canvas (loose components and then domains in rows, each domain a group holding its components, every node citing its Structure node), creating it the first time; a redraw keeps hand-drawn items and the edges between nodes still drawn, and a toast opens the canvas; every dropdown on the page shows icon tiles; branches open and close on the shared springs and fade as they go; a component's `kind:` is one of the canvas component kinds (`structure.ComponentKinds`) and `tech:` is free text; a component lists and edits its deploy targets per environment (provider from the integration catalog plus a resource name, `deploys:` in Polter). - Canvas: many canvases per project, all of one generalist type (`canvas`). Removal is soft: docs and canvases are archived (`archived_at`; hidden from lists, search, context, and agent reads, restorable from each surface's Archived view), and Work cards and Structure nodes keep `status = removed`. The core permanently deletes only an archived item and never a Decision; decisions move through their lifecycle instead.

Scope is a global filter, not a surface: each scoped page edits the one shared selection from its PageToolbar filter menu, with repeatable tokens (`domain:`, `component:`, and `env:` on Knowledge Docs and Activity; Structure always shows the whole tree and has no filter). Node tokens are one union sent as `scope_nodes` (a parent includes its children; ancestors stay included because the read is non-exact). It narrows Work cards (through their component), Rules, Decisions, Facts, Inbox, Activity, the Context Compiler, `polterware query|status|inbox|search --scope <node> [--exact]`, and the MCP `scope` argument. An entity has any number of contexts (the `entity_contexts` table, `scope_node_ids` in the contracts); a filter matches it when any context matches, and none means the whole project and stays visible under any filter. Rules, Decisions, and Facts take `scope: a, b` in Polter; the brief picks a decision through any of its contexts, and context-free decisions form its `principles:` line. `polterware scope <kind> <id> [<node>...]` replaces the contexts, and derived Inbox items are scoped with `polterware scope item <key> <node>...`.

While a Work card is open, Commander lists Copy agent brief (`polterware brief <slug>` to the clipboard) and Dispatch this card (Runs' Start run with the card and a prompt filled in, `DispatchPage` `startDraft`) first.

Keep history controls, the Home button with the breadcrumb after it (the project, whose crumb opens Switch project: a search, each project on its folder tile, and New project; then the list you are in, a tab of its own such as Decisions or Tiers or else the section, with no section group; then what is open in it, cut with an ellipsis: the milestone board, the canvas, the run, or the card, doc, or decision; the list crumb and a board under an open card navigate back), Commander (its input also takes an agent prompt: a query that matches no command reads as a run, so the search icon turns into Play, Run an agent is the one row, and the Route, Milestone, and Card pills open under the search; Enter runs a matching command or else starts the run, Cmd+Enter always starts it, at once, on those pills (Start run's, from `@polterware/feature-dispatch/run-route`; the open card comes preset), and Runs opens on it), App settings, and Project settings. ## UI law

`DESIGN.md` and `@polterware/frontend-design-system` are the visual source of truth. Product features must use shared `Input`, `Textarea`, `Select`, `Field`, `Button`, `Card`, `Surface`, Ark-backed overlays, `PageToolbar`, `FilterChip`, `DataTable`, `IconTile`, `StatusChip`, `EntityMenuButton` with `EntityContextMenu` (one action list for "…" and right-click), `PropertyPicker` (in a row, `PropertyPills`), `TokenPicker`, `RadioGroup`, `OptionTile` (leading every option of a list in a popover), `Morph` (a button that turns into its own confirm), `Peek`, `EntityNavigator`, and the global `DetailPanel` where applicable.

Prefer minimalist icon-only buttons with the shared tooltip (the `aria-label`) over text buttons in toolbars and page chrome; see `DESIGN.md`.

Do not hand-roll shared control chrome, menus, dialogs, operational tables, or entity panels. Use only radius and color tokens. Structural surfaces and text are opaque; alpha is limited to shared border, shadow, scrim, and transition tokens. Exception: on macOS the main window title bar and sidebar may use Electron vibrancy with `--color-shell-glass` washes; Commander and other product chrome stay opaque. Hugeicons Free Stroke Rounded is the only product icon set.

Do not add Markdown design or planning documents. Record decisions and work in the Polterware store (`polterware apply`); put unshipped direction in `docs/future.md` and delete items from it when they ship.

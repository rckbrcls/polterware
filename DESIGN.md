# Polterware Desktop Design

This document defines the active visual and interaction contract for the first version.

## Product frame

Polterware is a dense local operator workspace, not a generic dashboard. Prefer calm hierarchy, compact controls, opaque surfaces, restrained borders, and minimal decorative effects. Use the shared design tokens and primitives in `@polterware/frontend-design-system`.

The application opens on Inbox. The project sidebar is fixed:

```text
NOW
  Inbox
  Activity

PROJECT
  Milestones
  Canvas
  Structure
  Truth

DISPATCH
  Runs
  Routing       Tiers, Learning
  Usage         Agents, Stats

FOOTER
  Project settings
```

Settings is a dialog with a grouped rail and one concern per page, opened in one of two scopes. Project settings (sidebar footer) holds Project (General, Repositories, Environments, Danger zone — archive project) and Platforms (Connected, Catalog). App settings (title bar gear) holds Agents (MCP server, Agent setup, Hooks, AI skill, CLI reference) and App (Shortcuts, Appearance, Local core, Privacy, Danger zone — reset local store). Every rail entry and entity or shortcut list row uses a Hugeicons Free Stroke Rounded icon.

The title bar contains history controls, Home (Projects), drag space, Commander, and App settings. The sidebar follows Linear's rhythm: 28px items on a ~30px pitch with an 8px radius, 28px sentence-case group labels at 12px/500 in muted text, and 8px between groups. A group label is a button that collapses its group (the chevron shows on hover and stays while collapsed); a collapsed group keeps only its active row, and the choice is remembered on this computer. `[` toggles the whole sidebar. The Projects home is a Linear-style list on the shared `DataTable` (48px rows without separators, a 32px header of sortable 12px labels, a 16px icon tile and the name at 13px/500, other cells 12px/500 muted), under a 44px header and an "All projects" view pill. Project switching happens on the Projects screen, not in the title bar. Scoped pages edit one shared scope selection from their PageToolbar filter menu, which offers grouped `system:`, `domain:`, `component:`, and, on Truth Docs and Activity, `env:` tokens (Structure has no filter). Active scope tokens render as filter pills below the toolbar; scope is inclusion-only, one pill per level. Node tokens are one union of Structure nodes (a parent includes its children) and always include ancestors (non-exact); exact scope remains a CLI/MCP capability. There are no unrelated title-bar actions.

## Shared primitives

| Need | Required primitive |
| --- | --- |
| Text, password, search | `Input` and `.control-field` |
| Multiline input | `Textarea` |
| Selection | `Select` |
| Labeled control | `Field` |
| Stack of fields | `FormStack` |
| Icon + name record field | `IconNameField` |
| Actions | `Button` |
| Navigation actions | `LinkButton` (native anchor with shared button materials) |
| Nested section | `Card` |
| Elevated host | `Surface` |
| Dialog | `Dialog` or `A11yDialog` |
| Anchored surface | Ark-backed `Popover` |
| Compact menu | `MenuPanel` and `MenuItem` |
| Tabs | Ark-backed `Tabs` |
| Site navigation (public website) | Ark-backed `NavigationMenu` with `NavigationMenuPreviewPanel` |
| Section toolbar | compound `PageToolbar` |
| Filters | `FilterChip`, `FilterPopover`, or `ActiveFilterBar` |
| Operational collection | compound `DataTable` |
| Status | filled `StatusChip` |
| Entity details | global compound `DetailPanel` |
| Domain identity | `IconTile` |
| Loading placeholder | `Skeleton` / `PageSkeleton` (via `PageLoading`) |

An entity's actions are one `EntityAction[]` list, shown by its "…" `EntityMenuButton` and by right-click through the page's single `EntityContextMenu` (`createEntityContextMenu`); never write the same items twice. A new `group` starts after a separator, destructive actions go last in their own group, and `hint` names the shortcut on the right. A short list of values for one property (stage, milestone, kind) is a `PropertyPicker`: type to filter, arrows and Enter, a digit 1–9 for the nth option while the filter is empty, and a "Create" row when `onCreate` is given.

Menu rows (dropdown and context menus) always lead with a 14px Hugeicons icon before the label; this is law. Every `ContextMenu.Item` and `MenuItem` carries an icon, and a menu never mixes rows with and without icons. Only checkable rows (switches, checkmarks) and pure value lists may omit it.

Filters are Linear-style and built from `FilterPopover` + `ActiveFilterBar` over one `FilterField[]` and a `FilterClause[]` per page (`matchClauses` applies them). Every add creates a clause, shown as a segmented pill `[icon Field] [operator] [value] [×]`; clauses combine with AND and the operator switches between is / is any of and is not. Value lists use checkboxes (hidden until hover unless checked): clicking a value's label picks just that value and closes, the checkbox keeps the list open. Single-value fields end rows with a check mark. Saved filters live in the store per project and page, at the end of the filter menu, and Save sits beside Clear in the bar. Selection lists anywhere use `CheckboxRow`; `SwitchRow` is only for on/off settings. `F` opens the page's filter menu.

Toolbars and page chrome are minimalist and icon-first: actions are icon-only `Button`s (`size="icon"`; ghost for secondary, texture for navigation such as back, `ToolbarIconButton` for the primary create action) whose `aria-label` becomes the shared tooltip. Do not add visible text labels, helper lines, or status chips to a toolbar when an icon and tooltip say the same; keep text buttons for dialogs, forms, and empty states. Choices that would need a `Select` in a toolbar open from an icon `DropdownMenu`. Editors with many tools group them in a floating `Surface` dock over the canvas instead of a crowded header.

Text fields (`input`, `textarea`, `select`, contenteditable, and `control-field` inputs such as steppers and time fields) never show a focus ring, on click or keyboard, in any app; focus reads through the caret and selection. Do not add `outline`, `ring` or focus `box-shadow` to a text field. Buttons, links and composite widgets keep the neutral keyboard focus outline from `accessibility.css`.

Product features must not reproduce focus management, Escape behavior, outside dismissal, portals, positioning, or presence when the shared Ark-backed primitive owns it.

Dialogs in every Polterware app (Polterware, Polterware Notes, and Polterware Vitals) never draw dividers: spacing alone separates header, body, and footer. Footer actions are passed as a fragment of buttons, never wrapped: the dismiss action (Cancel, Reject, Skip) comes first and sits on the left; the primary or destructive action comes last on the right. A lone footer action stays on the right. The shared dialog owns its spacing: 28px side inset on every region, 24px above the 16px title and below the footer; features do not re-pad the body.

Removal follows one rule: reversible actions run at once, and only what cannot be undone asks first. Archive (docs, canvases) and Remove from board (Work cards) apply once the reason is given (see below; canvases need none) and show a toast that names the item with an Undo action (`pushToast(message, tone, { action })`; a toast with an action stays 6s). Archived items leave lists, search and agent reads and appear only in the surface's Archived view (`ArchivedList`), opened from a texture icon toggle in the toolbar, where each row offers Restore and Delete permanently. Delete permanently is the only path that loses data; it asks through `requestConfirm`, which states what is removed and that it cannot be undone, and focuses its destructive button. Archiving a milestone asks first, because its cards move to the Backlog and do not return. Decisions are never archived or deleted: they are challenged or superseded. Each app shell mounts one `ConfirmRegion` next to `ToastRegion`.


### Form spacing

The label sits tight to its control: `Field` owns a 6px label → control gap. Space between fields is 14px and comes from `FormStack`. Never use `space-y-*`, `grid gap-*` or a per-app override of `.pw-field` to space a form, and never pad a `Dialog` body again (the dialog already pads it). A record that has an icon and a color puts them in the `IconNameField` tile beside the name, not in separate rows.

## Collections and details

Operational collections use `DataTable`, sortable data columns, a narrow unsortable final actions column when row commands are needed, and one explicit Hugeicons domain icon in the primary cell. Long descriptions and secondary metadata belong in the detail panel.

`DataTable` rows move focus with ↓/J and ↑/K, activate with Enter, and, when the row passes `onPeek`, open a `Peek` (a quick-look dialog with an Open action) on Space instead; Space or Escape closes it and focus returns to the row. A list that opens an entity page gives that page an `EntityNavigator` ("3 / 12", K and J for previous and next) and calls `focusDataTableRow` with the entity's row id when the page closes.

Docs, decisions, cards, facts, and runs share one two-column page structure, `RailPage`: Back, the breadcrumb, and the actions in the header, the content in the center, and the properties rail on the right. A run's column is a centered 880px measure (`RailPage` `wide`), and it pins its agent above the scrolling content (`RailPage` `lead`, outside the scroll so nothing passes under it, in a row that mirrors the scroll's so it stays lined up with the column while the rail comes and goes): the 28px bot, animated while the run works, and agent / model / provider, with any failed attempts as quiet rows. Its transcript fills the center with no title, shaped like the agent's CLI: 12px mono `›` steps, dimmed reasoning, and raw output, the reply as read-only 13/20 Markdown (`pw-md-editor--transcript`), and the core's event lines as status rows, and its metadata in the rail, with its next step (Verify, Merge, or Cancel) as the one primary button in the header. On these pages, groups are titled with `RailGroup` (an optional icon tile and the title) and separated by space alone: never cards. Milestones opens on the Roadmap: one 44px table of the boards, with no tabs, All cards (every card of every board) first and then each milestone with a state chip, a delivered/total `ProgressBar`, and the target date. A row opens its board, a history entry of its own, so Back returns to the Roadmap; the board's toolbar has Back (to the Roadmap) and its Board and List tabs at the start (Cmd+B switches them), the breadcrumb Milestones › name in the middle, and its actions at the end. A `Breadcrumb` always sits in the middle of its bar, in `PageToolbar.Center` or a document header between Back and the actions; the bar spaces its groups apart (justify-between), so the breadcrumb lands in the exact center only when both sides match. Tabs always sit at the start. Inline values in one line (agent / model / provider, kind / technology, counts) are separated by " / ", never a middle dot. Moving the active row marker (J/K, or a row that leaves the list) never opens the row; Enter or a click does.

The Inbox is master/detail: its list, grouped by Decision, Drift, and Verify with Item, Status, and Context columns, sits beside the item's detail, pinned open (`EntityDetailHost pinned`, which drops the close button). The first item starts active, J/K moves the active item (`DataTable followFocus`), and when it is resolved the next one takes its place. Operational lists (a milestone's List, the Inbox) use `DataTable density="list"`: Linear's 44px pitch (a 40px row and the 4px row gap) on one line. A `grouping` splits rows into sections under 36px headers on the subtle surface (collapse chevron, label, count), in the order the groups are listed; rows keep the table's sort inside each group, rows of an unlisted group follow under "Other", and empty groups stay so their "+" (shown on hover, `onAdd`) is in reach. A grouped body renders every row. How a list groups, orders, and which properties it shows live in its toolbar `DisplayOptions` (Grouping and Ordering selects, a direction toggle, and property chips), remembered per surface; showing or hiding a property measures the columns again. X selects the focused row. Bulk selection exists only where a batch makes sense (the Inbox and a milestone's List): the selection toolbar sits at the bottom of the page and offers only actions every selected row allows, and a batch is one write under one justification. A `DataTable` that is a page's content fills it.

New records open in one `Composer`, Linear's create dialog, never a form dialog: a crumb (project › New card), the title first, an optional description, property pills that open the shared `PropertyPicker` (a card's Stage, Milestone, Component, and Kind; a decision's Level and Scope; a doc's Type and Scope; a fact's Kind and Subject), short labelled fields such as a doc's Path, and an optional Why. Enter in the title moves to the description, ⌘Enter creates, and Create more keeps it open with the same properties for the next record; a failed write keeps the draft. C opens the composer for the open surface (a card on Milestones and every other surface, a decision or a doc on Truth, a fact on Facts), and "+" buttons open it with their group's properties set. A person's reason is optional: Why goes to the change's rationale, and Activity shows "No reason given" when it is empty. Only a change of intent asks for one through `requestReason`: challenging or superseding a decision, moving a card back to an earlier stage, and archiving cards or docs.

Keyboard shortcuts come from one catalog in `@polterware/frontend-state`: rebindable chords (Settings › Shortcuts; Cmd+B switches a milestone between the List and the Board, M moves cards to a milestone, H defers and D dismisses Inbox items), fixed G sequences (G then I Inbox, A Activity, M Milestones, C Canvas, S Structure, T Truth, R Runs, H Projects; the second key must follow within 1.2s), and the row keys above. ⌘/ (or ?) opens the searchable shortcuts panel that lists all of them with the person's bindings, and Commander shows each command's chord or sequence on the right. A bare-key shortcut (`[`, C, F, M, N, a sequence) never fires while focus is in a field, menu, or dialog (`isTypingTarget`); a sequence listens first, so its second key reaches no single-key shortcut of its own.

`DataTable` columns are resizable in every app. Once the first rows paint, each column starts at its content width (capped at 320px) plus a proportional share of the spare viewport width; columns with an explicit `width` keep it and the last resizable column weighs double. The widths then freeze and the table switches to a fixed layout so live data never reflows columns. The last resizable column absorbs the remaining width. Each other resizable column header has a divider on its right edge: an 8px target around a 1px line. Widths stay between 48px and 360px; a column can override them with `minWidth`/`maxWidth`. Its pointer and keyboard contract is the DetailPanel divider's: arrows move 16px (64px with Shift), Home and End jump to the limits, double-click resets, and Escape cancels a drag. Only widths someone set persist, through `columnWidthsKey`. Cell text in resizable columns is clipped without an ellipsis. A shared `.pw-inline-fade` mask fades the right edge only when the text overflows, and one tooltip per table shows the full value. Actions, icon-only and selection columns pass `resizable={false}` and keep their width, and multi-line cells pass `wrap`.

Static reference tables (for example the CLI reference options, commands, and keys) also use `DataTable`, with `sortable={false}` columns, `resizableColumns={false}`, no row activation, no primary-cell icon, and wrapping description cells. The operational-collection rules above do not apply to them.

Entity detail uses the single lateral `DetailPanel` hosted by `MainSurface`, inside the central surface on its right side. `DetailPanel.CollectionHeader` mounts collection controls in a full-width upper band: `PageToolbar.Root` and `ActiveFilterBar` join it automatically inside the panel and render normally outside it. Toolbar padding is `8px 8px 4px`; wrapping controls and active filters determine the header's natural height. A separate workspace below contains the collection, sidebar and divider. Opening, closing, resizing or expanding details never changes the header width or disables its controls. The opaque, rounded panel reserves a column beside the collection by default; closing returns that width. Structure uses overlay mode across Map, Components and Relations: opening details preserves the collection width and places the panel above it, below the collection toolbar. In Map, collection controls float directly over the canvas with no background band; blank toolbar space passes pointer input through to the map. The shared panel measures the collection header so details and their resize handle still start below the controls, including wrapped toolbars and expanded details. The default lateral width is 400px, with a 320px minimum and 720px maximum, fitted to the available workspace. Its 8px divider supports direct pointer resize, cancellation, keyboard arrows (16px; Shift 64px), Home/End limits and double-click reset. A separate numeric sidebar-width key stores the preference; temporary host changes never rewrite it. Only old numeric widths migrate from the original key; floating geometry stays intact. Collection toolbars order search, filters and auxiliary actions before creation actions, with the primary creation action last; visual and keyboard focus order match. Every `PageToolbar` beside a `PageContent` (or heading a DetailPanel collection) has no band of its own: it overlaps the top 44px of the content, its blank space passes pointer input through, and the content's first child starts below it, so the controls float over the content as it scrolls (`--pw-toolbar-overlay`, `--pw-content-overlay` in tabs.css). An `ActiveFilterBar` and the lateral panel start below the toolbar controls.

Details start closed. Only explicit entity activation, including keyboard activation and entity navigation, opens them; changing collections closes them while preserving a valid selection. There is no toolbar opener or toggle slot. Cmd/Ctrl+J closes open details, and the expansion shortcut also requires an open panel. The detail header contains close and expand/restore controls. All entity titles render in the fixed header through `DetailPanel.Title` or `DetailPanel.Header title`. Expandable details center the title and icon between the expand/restore control on the left and close on the right; close-only details align the title to the left and close to the right. In expanded mode, Back replaces expand/restore and preserves the centered title. Metadata remains in the scrollable content with 20px lateral padding. Editable document titles preserve their input handlers in the header; the full Notes writing canvas keeps its own title editor, while its properties detail shows the note title in the header. `DetailPanel.Footer` holds fixed actions below the scroll viewport without a separate background strip; Inbox buttons use decorative 14px icons, share the full available width equally and remain visible while content scrolls. Expanded details occupy only the workspace below the collection header and restore to the saved lateral width. Escape cancels a resize, restores expansion, or returns focus to the selected item. Outside dismissal starts only on a completed click, including keyboard-generated clicks, preserving the clicked action and focus. Press-and-hold, movement of at least 3px, scrolling and cancelled gestures do not dismiss; tracking never takes pointer capture from the collection or Structure. Closing disables panel input immediately and animates a 16px rightward translation and fade with the 160ms `spring.slow.exit`. The departing frame retains its lateral or expanded geometry; its lateral reservation releases together with hiding the frame at the end of the exit, never on pointer release. Reduced motion removes travel and keeps the 60ms `spring.fast.exit` fade. Reopening interrupts the exit from the current pose, and stale completion callbacks cannot hide reopened details. Panel content, registered owned portals including callback confirmations, and common `data-detail-opener` activators are exempt. Empty, loading and error states retain controls; unavailable collections hide them. Features do not create another entity inspector, detail route, drawer or modal.

`FloatingWindow` is a reusable design-system compound component, independent of entity selection and shell shortcuts: `Root` defines the boundary and controlled `open`, `minimized`, `expanded` state with `onOpenChange`, `onMinimizedChange`, and `onExpandedChange`; `Workspace` holds the background; `Content` mounts arbitrary window content; optional `Header` customizes chrome styling. Shared controls exist without content, with unique per-instance IDs. No product surface currently mounts a floating window. The existing geometry in `polterware.shell.detail.width` remains available for a future caller's optional `storageKey`. Without a key, geometry remains session-local.

The floating window preserves its opaque raised shell, shared radius, subtle rim and soft lift; default 520 × 420px at bottom right with a 16px margin, minimum 320 × 280px fitted to smaller hosts. Four corners and four edge midpoints are the eight docks; ties retain the current dock. Card and 48px minimized circle share the dock. Dragging follows freely and settles to the nearest possible component position with `spring.moderate`; four edges and four corners resize via 8px targets. Versioned geometry persists dock and dimensions, accepting old numeric widths and normalized anchors; host changes fit without rewriting preferences. Red closes, yellow minimizes, green expands/restores. The same yellow button becomes the draggable reopen circle, preserving focus. Closing uses the fast exit and leaves no circle; outside activation closes without consuming the action, excluding owned portals and `data-floating-window-opener` activators. Expansion disables gestures and restore recovers geometry. Arrow keys (16px; Shift 64px) move or resize, docking on release; Escape cancels gestures or restores expansion. Pointer capture, 3px dead zone, release-click suppression, rollback, reduced motion and cleanup remain shared behavior. `createDragMotion` and `motion` supply interruptible tracking and `spring.slow` morphs with unscaled content; the first paint does not animate.

Operational records use the record layout: the shared record container supplies 16px top, 20px lateral and 24px bottom padding, while `DetailPanel.Main` holds overview text, tables, and notes; an optional `DetailPanel.Rail` holds `DetailPanel.Properties`, a label/value list where empty values are hidden (or offer an explicit add affordance). The rail stacks below the main column when the panel is narrower than 720px. Main and Rail have no additional padding inside record layouts; a shared 12px grid gap separates them. Record rows align to the start so spare height never stretches the space between groups. Documents (Docs, Decisions, Facts, Work cards) are full pages laid out like a Linear issue (`KnowledgeDocumentShell`): a 44px header with Back, the trail (`Truth › Docs › title`, 13px/500, the title in primary text; each step before the title is a link: a step for the page's own section, or for the tab it was opened from, closes the page back to that list; any other step opens its place) and a flat rail toggle; a 654px text column centered in the room the rail leaves, with 62px of page padding on both sides with a 24px/32px/600 title (32px above, 8px below) and the Markdown editor's `document` variant (`pw-md-editor--document`: 15px/24px/450 prose, 16px between blocks, its editing gutter outside the column); and a 376px properties rail on the right edge, at least 48px from the text, with no fill or frame. A Fact has no Markdown body: its column lists the evidence that backs it, and its rail holds Kind, Subject, Scope, and Origin. The rail holds `RailGroup`s titled with a 24px icon tile (Properties, Labels, Links, and on a Work card its Tasks, Questions, and Invariants; 13px/500 headings) and `DetailPanel.Properties variant="rail"`, whose values are ghost pills (28px, radius full, hover fill only); destructive actions close the rail after a hairline. It is open by default, remembered per app, and becomes a drawer on pages narrower than 900px. Its toggle is a bodied (`texture`) icon button, and it enters and leaves like the detail panel: a 16px slide to the right and fade on `spring.slow` (a quicker tween out), and beside the text its width closes while its content, kept at full width, travels to the page's right edge as it fades, dissolving 120px before the edge (a moving mask) instead of being cut by it, and the centered column glides to the middle at the same time instead of jumping; under reduced motion only the fade remains. A Work card's page adds its next steps between the intent and the Activity, each a `RailGroup` 32px apart with no card: the stage gate (its checks as 13px lines with an X for an error and a hint icon otherwise, and its Move to Plan / Move to Build button in the title row, disabled while an error holds it), Verification (Verify in the title row; pass, fail, and manual lines), the last handoff (Goal, Done, In progress, Next as a label/value grid, agent / branch / time in the title row), the runs that name the card (44px rows with the status chip, prompt, and agent / time), and the Agent brief (Preview and Copy in the title row; the brief in a 12px mono block on the subtle surface). A document ends with an Activity section, as on a Linear issue: a hairline and a 13px/500 title 48px below the content, then one line per change (a 20px actor icon, the actor in primary text, the summary, the relative time muted) with the rationale below it in muted text, never a card; a run of the same actor making the same change folds into its latest line, and the section is hidden while the entity has no history. The Activity page groups its table by day under the shared group headers. Documents never open the floating detail frame and have no cover. Detail sections in Polterware and Polterware Notes are never cards: `DetailPanel.Section` is separated from its siblings by 24px of space, and a titled section with an icon shows it in a 24px `IconTile` (optional `tone`) 8px before a 13px primary title, as `RailGroup` does; indicators and actions remain on the right. Untitled action sections have no heading icon. A record's kind and status chips flow after its title's last word and wrap with the text (`DetailPanel.Header` `aside`), not above its sections. Inbox Options uses a compact numbered informational list with 8px between rows; choosing and confirming an answer remains in the Decide flow. Main and properties columns have no divider line. Markdown editors retain their existing writing surface. There is no shared span grid; section chrome belongs to the shared `DetailPanel.Section`, not feature-owned cards.

## Spacing and grouping

Separate sibling content groups with spacing, not divider lines. Do not add `border-t` / `border-b` rules or `<hr>` between entries in a list, section, or document; use a consistent gap scale instead (tighter inside a group, wider between groups). Borders stay on shared chrome — page headers, controls, surfaces, and tables — where they define an object, not a gap.

Reference and long-form reading pages use a single centered column (`mx-auto w-full max-w-3xl`) inside `PageContent`, with generous vertical padding. A reference that lives in Settings (the CLI reference) uses the settings panel width and has no summary of its own: the settings rail and search are its navigation, and the grouped command index links to each command section.

## Surface and color rules

Structural fills are opaque shared neutral tokens. Text and labeled icons use opaque semantic colors, with icons inheriting `currentColor`. Do not add ad-hoc `rgba`, alpha hex, Tailwind opacity modifiers, `color-mix(... transparent)`, or translucent product chrome.

Every raised object wears one lit material, taken from the OpenCode reference (`docs/design-references/opencode.json`): light comes from above, so an object has a dark drop and a lit edge: a bright 0.5px top band that follows every radius and fades along the corners, over a faint 0.5px rim for the sides and bottom, never one continuous ring. The edge is drawn inside the box at its outer edge (`--material-edge`, `--material-edge-quiet`), so no overflow-clipping parent can cut it. Only the drop sits outside. Texture buttons carry the edge on their face, which covers the button box. Fills stay opaque and nearly flat; the edge is never a painted frame (`--field-frame` is transparent and has no width, so the lit edge sits at the component's outer edge; field focus is an inner primary ring). Use the shared shadow tokens, never a hand-written stack: `--material-control` for buttons, fields, chips and checkboxes; `--material-raised` for host surfaces and cards; `--material-float` for menus, popovers, dialogs and tooltips; `--material-hairline` for groups nested inside a raised host. Recessed tracks (tabs, segmented controls, switch tracks) take `--material-well`, the inset 0.5px chip rim with no drop, so only their active pill reads as raised; that pill is the near-flat control face with `--material-control`, never a thick inner frame. Pills, round buttons and the split history pill draw one 0.5px ring hugging the outside of the box, brightest on top and fading down (`--material-rim-fade` or the `material-rim-fade` class), plus the drop. The main panel wears `--material-edge-quiet` on an overlay above its content, so the toolbar never covers it and the sidebar column never clips it. Their alpha lives only in `--material-rim`, `--material-highlight` and `--material-drop` (and their `-strong` steps). Input wells are recessed, a step darker than the surface they sit on. Switches are squared (6px track, 3px knob; 4px and 2px when small), with a light knob and the info blue only when on. The previous material (keycaps, framed texture faces and four-ring cards) is kept for reference in `docs/design-references/polterware-classic/`.

Covers and tiles reuse the shared chrome finish (a chromatic metal reflection derived from an accent color). `AuroraCover` paints it over the whole cover. `IconTile` is a frameless neutral tile in the lit control material whose mark is cut out of the chrome finish (the default `chrome-mark` finish); `chrome` paints the whole tile and `plain` keeps the mark neutral. Use the tone, brand, or aurora options for the accent; structural surfaces stay opaque neutral.

Exception — macOS Desktop window chrome only: the main window title bar and sidebar may use shared `--color-shell-glass` / `--color-sidebar-glass` washes so frosted Electron vibrancy shows through while keeping the quiet dark cast. Commander (in-app palette and global overlay) uses the same opaque `surface-panel-float` material as other product dialogs. All other product surfaces, text, dialogs, and cards stay opaque. Settings Appearance → Reduce transparency disables main-window vibrancy / frost and restores opaque title bar and sidebar. Do not extend this exception to Commander, other in-app dialogs, cards, or other platforms.

Polterware, Polterware Notes, and Polterware Vitals share one lifted dark neutral ladder from `base.css`: canvas, shell, and sidebar `#131313`, surfaces stepping from `#161616` to `#232323`. All apps use dark mode exclusively, regardless of system appearance or saved theme preferences. Theme selectors and light palettes are unavailable; shared semantic tokens remain the foundation for future themes.

Use only these radius roles, from tightest to most generous:

- controls: `--radius-control` (10px)
- menu rows: `--radius-item` (10px)
- menus and popovers: `--radius-menu` (16px)
- nested cards: `--radius-card` (16px)
- host surfaces: `--radius-surface` (22px)
- floating windows: `--radius-window` (24px)
- dialogs: `--radius-dialog` (30px), applied by the shared dialog to every app's dialogs
- pills, avatars, switches, and dots: `rounded-full`
- flat buttons (ghost and icon variants, dialog and drawer close buttons): `rounded-full`, so their hover fill is a pill or a circle; solid buttons are keycaps (a body falling from white to grey with a 1px rim and a solid lip, and a concave face on `::before` whose gradient runs the other way, rounder at the bottom and with more body below it than above; `--keycap-*` tokens) and keep `--radius-control`; icon-size solid buttons are round keys. Pressing drops the key by `--keycap-travel` on `spring.fast`, flattens the lip and sinks and darkens the face; it releases on `spring.moderate`, and hover only tints. A ghost button that sits in a list of rows (for example a sidebar entry) takes the row's `--radius-item`.
- the Polterware Desktop (main window and Commander) wraps its root in `TextureFaceProvider`: every solid button there, icon-only ones included, renders the texture face, one near-flat opaque face lit by `--material-control` whose frame shows only while pressed (primary and brand take the `primary` texture tone, the info blue (`--tone-info-*`) of the info badge, danger the danger tone, secondary neutral; an explicit `textureTone` wins). Keycaps stay in the library and in apps that do not opt in.
- buttons inside floating card surfaces (Dialog and SettingsDialog, Popover, Drawer, FloatingWindow, DetailPanel, Commander) never wear keycaps: every text button there renders the texture face through `FloatingSurfaceProvider` (primary and brand take the brand tone, danger the danger tone, secondary and ghost neutral; an explicit `textureTone` or texture-capable `tone` wins). Icon-only buttons stay flat. `keepVariant` keeps the declared variant only for controls that are not actions, such as calendar occurrence chips.

Nested radii stay concentric: an inner panel's radius is the outer radius minus the inset between them (for example `calc(var(--radius-dialog) - 0.5rem)` inside an `p-2` dialog).

Cards whose content can scroll put `.pw-scroll-fade` on the scroller (tables inside it fade too): a shared mask fades the top edge under the header and the bottom edge only while content continues past them. It is a mask on opaque content, not translucent chrome.

Card has two shared opaque finishes: `variant="rings"` (default `.card-panel` / `.card-texture`) is a flat `--color-surface-subtle` face with the lit rim (`--card-rings`) and a soft drop; `variant="texture"` (`.card-texture-framed`) keeps the texture face geometry with a softer surface palette and no button hover or press behavior. `texture="compact"` uses the recessed field well and the control material, for small controls that should not look like buttons. Branch cards open and close their children like the shared collapse: the children and their elbows grow to their measured height on `spring.moderate` and fold on its exit tween (Ark's `hidden` is lifted so the fold can play), fading with it: in on the same spring and out early (an ease-out over the fold's ease-in), so rows are gone before the edge cuts them; reduced motion keeps only the fade in. `animateCollapse` takes the same fade with `fade: true` and a slower `tier: "moderate"` for larger regions. TreeView `branches compact` is a plain file tree: flat 28px ghost rows with no card material (hover and selection tint the row fill), 16px keys, a 6px leaf dot, and the same elbows at a 22px indent. Structure is a master/detail page with no divider: the compact tree on the shared ring Card in a 280px pane on the left, as tall as its rows, which the texture sidebar button at the start of the toolbar hides and shows like a document's rail (its width closes on `spring.slow`, a quicker tween out, while the card slides 16px and fades; reduced motion keeps the fade; the choice is remembered) (the title alone, with no icon, and only Add child on hover or focus, a bare 20px + with no hover fill; no row menu), and the selected node's document on the right, the central column of a docs page with no rail, laid out like a Linear project overview with space alone between subjects and edited in place: a 36px kind tile with the node's actions (`EntityMenuButton`) at the header's top right, the title and the description as its summary (`.pw-document__ghost-field` on the shared Input and Textarea: no chrome, committed on blur or Enter, Escape restores); then labeled lines (a 104px muted label column, values inline with a muted icon and 20px between them): Properties (level, a kind picker and a technology field on the shared `PropertyPicker`) and Checkout (a repository picker, a folder field, and the path in mono); a list of many things is a table, never inline chips; then, 56px below, a `CollapsibleSection` on the ring Card (from its heading to its rows, 16px apart; the heading's 24px icon tile, title, count, and chevron line up with the rows' tiles, titles, and statuses, and while open a 0.5px divider runs under it edge to edge) for Uses (a row opens that node; × removes the dependency, + adds one), Deploys (the resource, provider / environment, and a warn "CLI not connected" chip; the pencil in its heading opens the deploys editor), and each kind of record that cites the node (Cards, Decisions, Facts, Docs) with its count and a + in its heading (`actions`) that links one more, each a headerless `DataTable` of rows (a tile, the title, the stage, state, kind, or type on the right, and × to unlink a direct link on hover) that open their pages. The toolbar holds only the tree toggle: no search, filter, or add button. Document fields never change on hover or focus (no gradient, no fill), on every document page. A record section with nothing linked shows the shared `PageEmpty` with the bot ("No decisions yet", link one with +). Empty lines and sections that cannot be linked are left out, and the project's document lists everything. A click or the arrow keys select a node and its row stays selected; the project shows first. The collection registers with `details: false`, so no global detail panel opens. What all four share: 13px UI text with 12px meta and weights held between 400 and 550; 28px default controls; a 4px spacing grid; a radius ladder that stays at or below 12px for chrome (4px small, 6–8px controls and rows, 8–12px cards, panels, menus and the command palette) with full pills only for chips and avatars; hairline alpha borders with ring-shadow elevation; 14–16px icons; and 120–200ms motion. Polterware's radius ladder runs about twice as round (14px cards, 16px menus, 22px surfaces, 30px dialogs) and its page header matches Linear's 44px (`--page-header-height`, shared by `PageHeader`, `PageToolbar`, and the document trail).

The full measurements live in `docs/design-references/` (`linear.json`, `opencode.json`, `supabase.json`, `vercel.json`): color ladders and status scales, surfaces, borders, shadow stacks, typography roles, layout regions with their paddings, component states (hover, selected, open), and motion curves. Each reference is weighted for what Polterware takes from it:

- **Linear — screen organization and motion (primary).** Sidebar on the window background with the main content in one rounded panel inset 8px (12px radius, 0.5px border); 244px sidebar with 28px rows on a 29px pitch; 44px header and view bar; 44px list rows whose hover is an inset rounded fill; 36px sticky group headers; detail pages as a 668px reading column plus a 376px sticky properties column whose empty values read as muted prompts; one sliding highlight inside menus; instant hover, 150ms fades, and a 300ms spring for dialogs.
- **OpenCode — component material and borders.** Raised objects are lit from above: a dark drop, a 0.5px white rim and a brighter 0.5px top edge (`0 1px 2px #000@40%, 0 0 0 0.5px #fff@20%, 0 -0.5px 0 #fff@10%`); fills are translucent white over the layer below, inputs are recessed with a 2% top gradient, switches are squared (24 × 16 track, 12px knob), hairlines are 0.5px, and only two weights are used (440 and 530).
- **Supabase — targeted patterns.** Shortcut sequences taught inside tooltips, a breadcrumb title bar that doubles as the context switcher with environment badges, status badges built from a 10% fill, a dark border and a mid-tone text, and one card language shared by empty and promotional states.
- **Vercel — reference only.** Its gray scale and shadow ladder are kept for comparison; nothing is adopted from it by default.

## Execution honesty

Every screen must communicate whether an action is live, queued, completed, failed, unavailable, preview-only, or based on seeded demonstration data. Integration connect sessions report their actual core-owned state. A bounded inventory sync must not imply a complete provider graph, and no local action may imply a remote deployment or Cloud operation.

Motion may fade opacity only in transitions: presence keyframes in the shared popup, dialog, drawer, and toast CSS; boot splash and root cross-fade (`apps/polterware-desktop/src/renderer/boot-splash.css`, `apps/notes-desktop/src/renderer/boot-splash.css`); markdown editor dock visibility (`markdown-editor.css`); navigation menu viewport and content swaps (`navigation-menu.css`); template card enter keyframes (`template-card.css`); and Motion values in shared design-system motion primitives (the fluid hover highlight and gliding indicators). Resting surfaces stay opaque.

Run `pnpm design:lint` after UI changes. `tooling/check-ui-opacity.mjs` is the enforcement source; update this document before broadening its allowlist.
